# GNU/Linux Extensions to ELF

The GNU toolchain (binutils, glibc, GCC) and the Linux kernel have
introduced numerous extensions to the base ELF specification. These
extensions are not part of the formal gABI but are ubiquitous on Linux
systems and must be handled correctly by patchelf. This document catalogs
the extensions relevant to dynamic linking and binary modification.

## GNU Program Header Types

The main GNU-specific program header types reside in the OS-specific range
beginning at `PT_LOOS` (0x60000000). Their numeric values embed the ASCII
codes for 'G' (0x47), 'N' (0x4E), 'U' (0x55) in the hex digits of the
offset from `PT_LOOS` (e.g., 0x0**474E55**0), though these are not
byte-aligned.[^1] A fifth type, `PT_GNU_SFRAME` (0x6474e554), was added
more recently (see [Other Extensions](#other-extensions)).

| Type | Value | Introduced | Purpose |
|---|---|---|---|
| `PT_GNU_EH_FRAME` | `0x6474e550` | ~2001 (binutils 2.12) | Locates `.eh_frame_hdr` for exception handling |
| `PT_GNU_STACK` | `0x6474e551` | 2003 (Linux 2.6.6) | Controls stack executability |
| `PT_GNU_RELRO` | `0x6474e552` | ~2004 (binutils/glibc) | Marks region to be made read-only after relocation |
| `PT_GNU_PROPERTY` | `0x6474e553` | 2020 (Linux 5.8) | Locates `.note.gnu.property` section |

### PT_GNU_EH_FRAME

Generated by `ld --eh-frame-hdr`. Contains a sorted binary-search index
over `.eh_frame` FDE (Frame Description Entry) records, enabling O(log n)
lookup of exception/unwind info instead of linear scanning.[^2] The segment
specifies the location and size of `.eh_frame_hdr`.

### PT_GNU_STACK

The `p_flags` field (specifically `PF_X`) controls whether the process
stack is executable. The behavior when this header is absent is
architecture-dependent: on x86/x86-64, absence implies an executable
stack for backward compatibility; on other architectures (e.g., AArch64),
the default may be non-executable.[^3][^3a]

Introduced via a binutils patch in May 2003; kernel support added in Linux
2.6.6.[^4] The kernel uses only the *last* `PT_GNU_STACK` header if
multiple are present.[^5] Note the kernel's first/last convention varies
by header type: `PT_INTERP` uses the *first* entry, while `PT_GNU_STACK`
and `PT_GNU_PROPERTY` use the *last*.[^5a]

**Patchelf interaction**: Patchelf's `--print-execstack`, `--set-execstack`,
and `--clear-execstack` options directly modify the `PF_X` flag on
`PT_GNU_STACK`.[^6]

### PT_GNU_RELRO

Identifies a memory region that can be remapped read-only via `mprotect()`
after the dynamic linker finishes applying relocations.[^7] This is the
core mechanism of the RELRO hardening technique. Jakub Jelinek (Red Hat)
was the primary implementer, with patches dating to January 2004.[^8]

See the [RELRO section](#relro-relocation-read-only) below for full
details.

### PT_GNU_PROPERTY

The kernel uses this header to efficiently locate `.note.gnu.property`
without scanning all sections.[^9] Used for hardware security features like
Intel CET (Control-flow Enforcement Technology) and AArch64 BTI (Branch
Target Identification). Added in Linux 5.8 (2020).[^10]

The kernel prioritizes the **interpreter's** (ld.so's) last
`PT_GNU_PROPERTY` header; if the interpreter doesn't have one, the
executable's last `PT_GNU_PROPERTY` is used instead.[^10a]

**Patchelf interaction**: Patchelf synchronizes `PT_GNU_PROPERTY` with the
`.note.gnu.property` section when sections are rewritten.[^11]

## GNU Hash Tables (.gnu.hash)

### History

The initial design was done by Ulrich Drepper; the implementation was by
Jakub Jelinek, posted as a binutils patch in June 2006. The patch itself
states: "The initial design was done by Ulrich Drepper."[^12] The glibc commit `871b91589bf4f6dfe19d5987b0a05bd7cf936ecc` added
runtime support.[^13a] Fedora Core 6 (October 2006) was the first distribution to
use it by default.[^14]

### Section and Dynamic Tag

- Section type: `SHT_GNU_HASH` = `0x6ffffff6`[^14a]
- Dynamic tag: `DT_GNU_HASH` = `0x6ffffef5`[^14a]

### Comparison with SYSV Hash

| Feature | SYSV Hash (`.hash`) | GNU Hash (`.gnu.hash`) |
|---|---|---|
| Hash function | Custom: `h = (h<<4) + *s; if (g = h & 0xf0000000) h ^= g >> 24; h &= ~g;` | DJB2: `h = 5381; h = h*33 + *s;` |
| Bloom filter | None | Yes (2-bit positions per word) |
| Symbol ordering | Arbitrary | Sorted by `hash % nbuckets` |
| Undefined symbols | Included | Excluded (below `symndx`) |
| Chain termination | Separate `nchain` count | Lowest bit of chain value |
| Performance | Baseline | ~50% faster dynamic linking[^15] |

### Section Layout

The `.gnu.hash` section has four parts:[^16]

1. **Header**: 4 `uint32` fields: `nbuckets`, `symndx` (first symbol
   index in `.dynsym` that is hashed), `maskwords` (bloom filter size),
   `shift2` (bloom filter shift)
2. **Bloom filter**: Array of `maskwords` machine-word entries (32-bit on
   ELF32, 64-bit on ELF64). For hash value H, check word
   `(H / ELFCLASS_BITS) % maskwords` at bit positions
   `H % ELFCLASS_BITS` and `(H >> shift2) % ELFCLASS_BITS`
3. **Buckets**: Array of `nbuckets` `uint32` values mapping
   `hash % nbuckets` to the first symbol index
4. **Chains**: Parallel to `.dynsym` starting at `symndx`. Each entry
   stores `hash & ~1`, with bit 0 set on the last entry in a chain

### Linker Control

`--hash-style={sysv,gnu,both}` controls which hash sections are
emitted.[^17]

### Adoption Timeline

Fedora Core 6 (2006-10), Debian (2007), Arch Linux (2012-03), DragonFlyBSD
(2012-03), FreeBSD (2012-04), musl (2012-08), Android bionic (2014-11),
OpenBSD (2018-11), NetBSD (2020-02).[^14]

**Patchelf interaction**: When dynamic symbols are renamed, patchelf must
rebuild the GNU hash table. This requires reordering `.dynsym` entries to
satisfy the bucket-sorted ordering constraint, updating the bloom filter,
and remapping symbol indices in all relocation tables.[^18]

## GNU Symbol Versioning

### History

Solaris 2.5 (1995) introduced symbol versioning in its link editor
(`ld`) and runtime linker (`ld.so.1`).[^19a] In 1997, Ulrich Drepper
and Eric Youngdale adapted the Solaris mechanism for glibc, adding a key extension: the ability to have *multiple
definitions of the same symbol* at different versions within a single
shared object. GNU symbol versioning shipped with glibc in 1997-1999.
[UNVERIFIED: commonly attributed to glibc 2.1, released February 1999,
but the cited source gives only the year 1997 for the design work.][^19]

### Sections

| Section | Type | Value | Purpose |
|---|---|---|---|
| `.gnu.version` | `SHT_GNU_versym` | `0x6fffffff` | Per-symbol version index table |
| `.gnu.version_d` | `SHT_GNU_verdef` | `0x6ffffffd` | Version definitions provided by this object |
| `.gnu.version_r` | `SHT_GNU_verneed` | `0x6ffffffe` | Version requirements from other objects |

### How It Works

**`.gnu.version`** (version symbol table): A parallel array to `.dynsym`
where each `Elf_Versym` (`Elf_Half`) entry contains a version index:[^20]

- `0` (`VER_NDX_LOCAL`): Symbol is local, not available externally
- `1` (`VER_NDX_GLOBAL`): Unversioned global symbol
- `2`-`0x7ffe`: References a version in `.gnu.version_d` or
  `.gnu.version_r`
- Bit 15 (`0x8000`): Hidden bit -- symbol not visible to static linker

**`.gnu.version_d`** (version definitions): Linked list of `Elf_Verdef`
structures, each with auxiliary `Elf_Verdaux` entries containing the
version name (as a string table offset). The `DT_VERDEFNUM` dynamic tag
gives the count.[^21]

**`.gnu.version_r`** (version requirements): Linked list of `Elf_Verneed`
structures with auxiliary `Elf_Vernaux` entries specifying which version
from which shared object is required. The `DT_VERNEEDNUM` dynamic tag
gives the count.[^22]

### Toolchain Support

- **Assembler directives**: `.symver foo, foo@VER` (non-default reference)
  or `.symver foo, foo@@VER` (default definition) in GNU as.[^23]
- **Linker version scripts**: `VERSION { VER_1 { global: foo; bar; }; }`
  syntax assigns version tags.[^24]

**Patchelf interaction**: Patchelf's `--clear-symbol-version` sets the version index for specified symbols
to 1 (`VER_NDX_GLOBAL`, i.e., unversioned global).[^25] When replacing `DT_NEEDED` libraries, patchelf also updates
the `vn_file` field in `.gnu.version_r` entries.[^26]

## DT_RUNPATH vs DT_RPATH

### Dynamic Tag Values

- `DT_RPATH` = 15 (superseded by `DT_RUNPATH`; "level 2" in the gABI)[^27]
- `DT_RUNPATH` = 29

### Semantic Differences

| Behavior | DT_RPATH | DT_RUNPATH |
|---|---|---|
| Search order vs `LD_LIBRARY_PATH` | Searched *before* | Searched *after* |
| Transitive dependencies | When in the main executable, used when resolving all dependencies in the tree[^28a] | Only direct `DT_NEEDED` dependencies |
| When both present | Ignored | Takes precedence |

### glibc ld.so Search Order

1. `DT_RPATH` of the calling object (only if `DT_RUNPATH` absent)
2. `LD_LIBRARY_PATH` (except in secure-execution mode)
3. `DT_RUNPATH` of the calling object (if present)
4. `/etc/ld.so.cache`
5. Default paths: `/lib`, `/usr/lib` (and `/lib64`, `/usr/lib64` on
   64-bit), unless `DF_1_NODEFLIB` is set[^28]

### History

`DT_RUNPATH` was introduced to fix the problem that `DT_RPATH` overrides
`LD_LIBRARY_PATH`, making it impossible for users to override library paths
for debugging or testing.[^29] The GNU linker uses `--enable-new-dtags` /
`--disable-new-dtags` to control which is emitted; the default varies by
distribution. With `--enable-new-dtags`, both `DT_RPATH` and `DT_RUNPATH`
are emitted with the same value, but the runtime linker ignores `DT_RPATH`
when `DT_RUNPATH` is present. The binutils configure-time default has varied; the cited Debian bug
discusses the change in the context of binutils 2.28 packaging.[^30]

**Patchelf interaction**: Patchelf converts `DT_RPATH` to `DT_RUNPATH` by
default. The `--force-rpath` flag preserves `DT_RPATH` semantics.[^31]

## DT_FLAGS_1 and DF_1_* Flags

Dynamic tag `DT_FLAGS_1` = `0x6ffffffb`. These flags originated primarily
from the Solaris linker/loader and were adopted by GNU toolchains.[^32]

Selected flags relevant to patchelf and Nix:

| Flag | Value | Description |
|---|---|---|
| `DF_1_NOW` | `0x00000001` | Resolve all relocations at load time |
| `DF_1_GLOBAL` | `0x00000002` | Set `RTLD_GLOBAL` |
| `DF_1_NODELETE` | `0x00000008` | Cannot be `dlclose`'d |
| `DF_1_NOOPEN` | `0x00000040` | Cannot be `dlopen`'d |
| `DF_1_ORIGIN` | `0x00000080` | `$ORIGIN` substitution required |
| `DF_1_INTERPOSE` | `0x00000400` | Object is an interposer |
| `DF_1_NODEFLIB` | `0x00000800` | Ignore default library search paths |
| `DF_1_PIE` | `0x08000000` | Position-Independent Executable |

The full table includes approximately 30 flags; see glibc `elf.h` for the
complete list.[^33]

Note: `DT_FLAGS_1` is distinct from `DT_FLAGS` (value 30), which holds the
base `DF_*` flags. `DF_1_NOW` in `DT_FLAGS_1` and `DF_BIND_NOW` in
`DT_FLAGS` are semantically equivalent; some linkers set both.[^34]

**Patchelf interaction**: Patchelf's `--no-default-lib` sets
`DF_1_NODEFLIB` in `DT_FLAGS_1`, adding a new `DT_FLAGS_1` entry to
`.dynamic` if one doesn't exist.[^35]

## RELRO (RELocation Read-Only)

### Mechanism

1. The linker reorders sections so that data requiring relocations
   (`.got`, `.dynamic`, `.init_array`, `.fini_array`, etc.) is placed
   contiguously.[^36]
2. A `PT_GNU_RELRO` segment marks the virtual address range to be
   protected.
3. After the dynamic linker finishes applying all relocations, it calls
   `mprotect()` on the `PT_GNU_RELRO` region to set it read-only.[^37]

### Partial vs Full RELRO

**Partial RELRO** (`-Wl,-z,relro`):
- The non-PLT GOT (`.got`) is made read-only
- `.got.plt` remains writable for lazy binding
- `.dynamic` and other relocation data become read-only
- Minimal startup cost[^38]

**Full RELRO** (`-Wl,-z,relro,-z,now`):
- `-z now` sets `DF_BIND_NOW` / `DF_1_NOW`, forcing eager PLT resolution
- `.got.plt` also becomes read-only (since lazy binding is disabled)
- The entire GOT is protected, eliminating GOT overwrite attacks
- Trade-off: increased startup time[^39]

### Distribution Defaults

Fedora enabled full RELRO (`-z now`) by default starting with
Fedora 23 (2015) as part of the "Harden All Packages" initiative.[^40]
Other distributions have adopted full RELRO at various times.
[UNVERIFIED: the exact timeline for Debian's full RELRO default is
unclear; partial RELRO has been widely used but full RELRO adoption
varies by package.]

## GNU Notes

All GNU notes use the owner name `"GNU"` (4 bytes including null
terminator).[^41]

| Note Type | Value | Section | Purpose |
|---|---|---|---|
| `NT_GNU_ABI_TAG` | 1 | `.note.ABI-tag` | OS/ABI compatibility |
| `NT_GNU_HWCAP` | 2 | (various) | Hardware capability info |
| `NT_GNU_BUILD_ID` | 3 | `.note.gnu.build-id` | Unique build identifier |
| `NT_GNU_GOLD_VERSION` | 4 | `.note.gnu.gold-version` | Gold linker version |
| `NT_GNU_PROPERTY_TYPE_0` | 5 | `.note.gnu.property` | Program property notes |

### .note.ABI-tag

Contains a 4-word descriptor: word 0 is the OS identifier (0 = Linux,
1 = GNU/Hurd, 2 = Solaris, 3 = FreeBSD), words 1-3 are the minimum kernel
version (major, minor, patch). Used by the dynamic linker to verify ABI
compatibility.[^42]

### .note.gnu.build-id

Designed by Roland McGrath in 2007; added to binutils 2.18 via
`ld --build-id`.[^43] The descriptor contains a hash (typically SHA-1, 20
bytes) computed over the normative parts of the ELF output. Designed as a
unique identifier for matching (e.g., core dumps to debug info), not a
verifiable checksum. First deployed in Fedora 8.[^44] The section has
`SHF_ALLOC` so it is present in the loaded image.

### .note.gnu.property

Contains program property notes for features requiring linker and runtime
loader awareness:[^45]

- `GNU_PROPERTY_STACK_SIZE`: Requested minimum stack size
- `GNU_PROPERTY_AARCH64_FEATURE_1_AND`: ARM64 BTI/PAC flags
- `GNU_PROPERTY_X86_FEATURE_1_AND`: Intel CET IBT/SHSTK flags

The linker performs AND/OR operations on property values across input
objects.

### Note Alignment: The 4-byte vs 8-byte Conflict

There is a well-known discrepancy between the gABI spec and GNU/Linux
practice regarding note entry alignment:[^46a]

- The **gABI spec** states that 64-bit objects use **8-byte** alignment
  for note entries, and 32-bit objects use 4-byte alignment.[^46b]
- The **`elf(5)` man page** and GNU toolchain practice use **4-byte**
  alignment unconditionally, even for 64-bit objects.[^46c]

This means a spec-compliant 64-bit ELF file and a GNU-produced 64-bit
ELF file may use different alignment within the same note section.
Tools processing notes must handle both conventions.

**Patchelf interaction**: Patchelf handles note sections specially during
`normalizeNoteSegments()`, breaking compound `PT_NOTE` segments into
one-per-section.[^46] The original `sh_addralign` is preserved for note
sections when it is *smaller* than `sectionAlignment` (`sizeof(Elf_Off)`:
4 on ELF32, 8 on ELF64). This correctly handles the common case of
4-byte-aligned notes on 64-bit. However, note sections with alignment
equal to or larger than `sectionAlignment` have their alignment
overwritten unconditionally and not restored.[^46]

## Other Extensions

**`STT_GNU_IFUNC`**: A symbol type extension allowing indirect functions --
the runtime linker calls a resolver function to determine the actual
implementation address. Used for hardware-optimized function selection
(e.g., `memcpy` with AVX vs. SSE).[^47]

**`.note.GNU-stack`**: A section (despite the `.note` prefix, not a note
in the `NT_*` sense) that declares stack executability requirements. The
linker collects these from all input objects; if any requests an executable
stack, the final `PT_GNU_STACK` gets `PF_X`.[^48]

**`ELFOSABI_GNU`** (value 3): The ELF OS/ABI identification value for GNU,
replacing the older `ELFOSABI_LINUX` alias (same numeric value).[^49]

**PT_GNU_SFRAME** (`0x6474e554`): A newer segment type for the SFrame
(Simple Frame) unwinding format, a simpler alternative to
`.eh_frame`/DWARF CFI. Present in glibc 2.40 `elf.h`.[^50]

## Open Questions

- **DT_RELR / SHT_RELR** (compact relative relocations, added in
  glibc 2.36 / binutils 2.38 / Linux 5.17) are defined in patchelf's
  `elf.h` (`SHT_RELR`=19, `DT_RELR`=36, `DT_RELRSZ`=35,
  `DT_RELRENT`=37) but patchelf's `patchelf.cc` has zero references to
  RELR. If patchelf moves sections, RELR entries encoding relative
  addresses may need updating. This is an increasingly important gap as
  RELR adoption grows (Android, newer glibc). See
  [05-edge-cases-and-gaps.md](05-edge-cases-and-gaps.md#relr-relocations--critical-gap)
  for detailed analysis.
- How does patchelf handle binaries that use `STT_GNU_IFUNC` symbols?
  Does renaming such symbols break the resolver mechanism?
- Should patchelf update `DT_RELACOUNT`/`DT_RELCOUNT` when sections are
  moved? These tags are optimization hints for the dynamic linker.
- The gABI v4.3 draft makes `DT_HASH` optional. How should patchelf
  handle binaries with only `.gnu.hash` and no `.hash`?
- How do Solaris-specific `DF_1_*` flags interact with GNU ld.so?
  Patchelf currently doesn't validate flag combinations.
